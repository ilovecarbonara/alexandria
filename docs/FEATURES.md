# Feature Specifications

## F1: Authentication
- University email only (@uspf.edu.ph)
- Registration creates account with is_approved: false
- Admin must flip is_approved: true before user can log in
- Session management via Supabase Auth

## F2: Thesis Registration
- User uploads PDF + fills metadata form
- Fields: ordered author list, title, level (dropdown), category (dropdown), submission type (radio)
- The first author is the registering user's profile name, pre-filled and read-only. Users may add up to five more authors, for six total authors per thesis.
- Client and server validation reject blank, invalid, duplicate, or over-limit author lists. The server independently verifies that the thesis owner is listed as an author.
- If the user has existing draft registrations without a child revision, a "This is a revision of" dropdown appears — linking the new thesis as the next entry in a version chain (see F12)
- On submit:
  1. SHA-256 hash generated client-side via Web Crypto API — PDF never leaves the browser. Node crypto module is NOT used for registration.
  2. PDF deleted immediately after hashing — never persisted
  3. Duplicate check: query blockchain via isRegistered(hash)
  4. If duplicate → show error, stop
  5. If draft → proceed to blockchain registration regardless of other drafts
  6. Submit hash + metadata to smart contract → get tx_hash
  7. Save record to Supabase theses table (including title_normalized, previous_thesis_id if revision) and ordered rows in thesis_authors
  8. Trigger title similarity check (F8) — non-blocking, runs after save
  9. Show success state with tx link

## F3: Certificate Generation
- Generated on demand (not stored)
- Uses jsPDF + qrcode
- Contains: authors, title, level, category, submission type,
  sha256 hash, tx hash, timestamp, QR code linking to Sepolia Etherscan tx
- Authors are rendered under a single "Authors" label, one name per line.
- Certificate text frames the document as a REGISTRATION RECORD,
  not a proof of authorship
- If the thesis belongs to a version chain (>1 entry), the certificate includes a "Version History" table showing version number, type, SHA-256 hash, tx hash, and date for each chain entry
- Downloadable as PDF
- Regeneratable at any time from dashboard

## F4: Public Verification Interface (no login)
- Two modes: Search and Verify
- Search: keyword input + filters (level, category, submission type, date range) → returns
  thesis metadata only — never the PDF
- Search excludes pending-status theses (only accepted/flagged/rejected shown)
- Verify: upload PDF (hashed client-side) OR paste hash → checks blockchain
  → returns registration record or no match
- If the verified thesis belongs to a version chain (>1 entry), a version history timeline is displayed alongside the metadata

## F5: Dispute Flag System (Threaded)
- Any authenticated, approved, non-admin user can flag any thesis registration except their own
- A dispute is a 3-party email-style **thread** between **flagger**, **admin**, and the **thesis owner**
- Filing a flag creates one row in `disputes` plus an opening message in `dispute_messages` (`author_role: 'flagger'`); the flagger's `dispute_reads` pointer is set immediately so the opening message isn't shown as unread to themselves
- Disputes can also be auto-generated by the title similarity system (see F8) — the opening message is authored by the matched thesis owner with `author_role: 'owner'` and notes the similarity score and matched title
- Any participant (flagger, owner, admin) can post replies while the dispute is `open`. Replies are rate-limited to 30 per minute per user
- Identity rules:
  - The **flagger is anonymized** to the thesis owner ("Anonymous flagger") to discourage retaliation
  - The flagger sees the owner's real name; admins see everyone
- Each new reply inserts an `activity_logs` row for the two non-actor participants — these surface as recent-activity entries and contribute to the unread badge
- Resolution is admin-only via `PATCH /api/disputes/[id]` with a required `closing_note`. The note is appended as a final `author_role: 'admin'` message, then `status` flips to `resolved` (read-only at the DB layer — RLS rejects further inserts)
- Resolution does NOT alter the blockchain record or the thesis's own `status` (those are managed separately by the admin)
- Resolutions are rate-limited to 20 per hour per admin and notify both flagger and owner via `activity_logs`

## F6: Admin Dashboard
- Accessible only if is_admin: true
- Charts (Chart.js):
  - Pie/bar: thesis distribution by category
  - Bar: distribution by level
  - Line: registration volume over time (monthly)
  - Count display: open vs resolved disputes
  - Count display: title alerts (total, last 30 days)
- Dispute management table: paginated list of every dispute, filterable by status (all/open/resolved). Selecting a row opens the full thread (`DisputeThread`) inline; admins can reply while open and resolve with a required closing note
- Thesis registry table: view all theses, change status (pending → accepted/flagged/rejected)
- Title alert log table: view matched pairs, similarity scores, notified status — sortable by similarity and date via dropdown
- All admin tables are paginated (15 per page) with expand-to-modal for full details
- The Disputes sidebar item carries an unread-message badge (count of dispute messages authored by others since the admin's last `dispute_reads` pointer)

## F7: User Dashboard
- List of own registered theses with pagination (15 per page)
- Each row: title, status, date, tx hash link, actions (certificate download, version history)
- Content is truncated to one line with ellipsis; an "Expand" button opens a full-detail modal overlay
- "History" button appears on theses that participate in a version chain — opens a modal with a timeline view
- Browse Registry page (sidebar nav item): authenticated users can search/verify/flag theses using the same registry browser as the public verification page, with dispute flagging enabled
- Disputes page (sidebar nav item): two tabs — "Filed by me" (`listMyDisputes`) and "On my theses" (`listDisputesOnMyTheses`). The active tab defaults to whichever bucket has rows. Each row shows the counterparty, last-message preview, and unread count. Selecting a row opens the thread (`DisputeThread`) in a modal where the participant can reply while open
- Title Alerts page (sidebar nav item): table of similarity alerts scoped to the user, each with a dispute/flag action — sortable by similarity and date via dropdown column headers
- Alert count and active-disputes count displayed as stat cards on the main dashboard
- The Disputes sidebar item carries an unread-message badge (`countMyDisputeUnreads`) — sum of unread messages across both tabs
- Stat cards: registered theses count, active disputes, title alerts, recent activity

## F8: Title-Based Alert System
- Triggers automatically after every successful registration (step 8 of F2)
- Runs as a non-blocking background process — does not delay the
  registration response to the user
- Process:
  1. Normalize the incoming title (lowercase, strip punctuation,
     collapse whitespace) — store as title_normalized
  2. Fetch all existing title_normalized values from the theses table
  3. Query Supabase using pg_trgm similarity() function against 
   title_normalized column — threshold set via TITLE_ALERT_THRESHOLD env variable
  4. Collect all matches above the configured threshold (suggested default: 0.50)
  5. For each match, retrieve the owner (user_id) of the matched thesis
  6. Insert alert record to the title_alerts table (new_thesis_id, matched_thesis_id,
     notified_user_id, similarity_score, status: notified)
  7. If the similarity score meets the auto-flag threshold (default: 0.75,
     configurable via AUTO_FLAG_THRESHOLD env variable), automatically create
     a dispute record for the incoming thesis and set its status to flagged.
     The dispute is authored by the matched thesis owner with a reason noting
     the similarity score and matched title. Only one auto-flag dispute is
     created per registration, even if multiple matches exceed the threshold.
- The alert is informational only — it does not alter any record or
  trigger any automated action (unless the auto-flag threshold is met)
- Alerts are displayed in-system via the user dashboard and admin alert log
- Threshold is configurable via environment variable (TITLE_ALERT_THRESHOLD)
  to allow tuning without a code deploy
- A single incoming registration may trigger multiple alerts if it
  matches multiple existing entries
- Draft registrations also trigger the similarity check
- Same-owner matches are skipped entirely — no alert created (e.g., user registering a Final after their own Draft)

## F9: Thesis Status Workflow
- New registrations default to status: pending
- Admin can change status to: accepted, flagged, rejected
- Status changes are logged in activity_logs
- Public verification page displays thesis status alongside metadata

## F10: User Management
- Admin can view all registered users
- Admin can deactivate a user (sets is_active: false)
- Admin can reactivate a user (sets is_active: true)
- Deactivated users are signed out on next request and cannot log in
- Admin can reject a user (sets is_approved: false — soft, reversible)
- Admin can re-approve a rejected user
- last_active_at is tracked for user activity monitoring

## F11: Activity Logging
- Key user actions are logged to the activity_logs table
- Actions include: thesis registration, dispute creation, status changes
- Admin can view recent activity in the admin dashboard
- Logs are append-only and never modified

## F12: Version Chain
- Theses can be linked in a linear version chain via `previous_thesis_id`
- Each thesis has at most one predecessor and one successor
- Only draft theses without an existing child revision are available as revision targets
- Chain is displayed as a vertical timeline with version numbering (v1, v2, …), submission type badges, and current-entry highlighting
- Version chain appears in: user dashboard (modal), public verification (inline timeline), and certificate PDF (table)
- Chain data is built in-memory from the user's theses — walks backward to find the root, then forward to produce chronological order
- Cycle-safe traversal via Set guards

## F13: Settings
- User settings page: password change (current password verification + new password with confirmation)
- Admin settings page: read-only display of system configuration (blockchain network, contract address, title similarity threshold and its source)
